Now let’s consider Customer and Address tables and see all relationship scenarios with SQL + explanation.

1. One-to-One (1:1)

👉 Each customer has exactly one address.

Schema
CREATE TABLE Customer (
    customer_id INT AUTO_INCREMENT PRIMARY KEY,
    name        VARCHAR(100) NOT NULL
);

CREATE TABLE Address (
    address_id   INT AUTO_INCREMENT PRIMARY KEY,
    customer_id  INT UNIQUE,   -- UNIQUE enforces 1:1 relationship
    street       VARCHAR(200) NOT NULL,
    city         VARCHAR(100) NOT NULL,
    CONSTRAINT fk_address_customer
        FOREIGN KEY (customer_id) REFERENCES Customer(customer_id)
        ON DELETE CASCADE
        ON UPDATE CASCADE
);


✅ Here, customer_id in Address is unique, so one customer → one address only.

2. One-to-Many (1:N)

👉 One customer can have multiple addresses.

Schema
CREATE TABLE Customer (
    customer_id INT AUTO_INCREMENT PRIMARY KEY,
    name        VARCHAR(100) NOT NULL
);

CREATE TABLE Address (
    address_id   INT AUTO_INCREMENT PRIMARY KEY,
    customer_id  INT NOT NULL,  -- foreign key only (no UNIQUE)
    street       VARCHAR(200) NOT NULL,
    city         VARCHAR(100) NOT NULL,
    CONSTRAINT fk_address_customer
        FOREIGN KEY (customer_id) REFERENCES Customer(customer_id)
        ON DELETE CASCADE
        ON UPDATE CASCADE
);


✅ Now, the same customer_id can appear multiple times in Address.

3. Many-to-One (N:1)

👉 Multiple addresses belong to the same customer.
➡️ This is just the reverse view of One-to-Many (same schema as above).

4. Many-to-Many (M:N)

👉 A customer can have multiple addresses, and the same address can belong to multiple customers (rare, but possible in shared housing/office).
➡️ Requires a junction table.

Schema
CREATE TABLE Customer (
    customer_id INT AUTO_INCREMENT PRIMARY KEY,
    name        VARCHAR(100) NOT NULL
);

CREATE TABLE Address (
    address_id   INT AUTO_INCREMENT PRIMARY KEY,
    street       VARCHAR(200) NOT NULL,
    city         VARCHAR(100) NOT NULL
);

-- Junction table for M:N relation
CREATE TABLE Customer_Address (
    customer_id INT,
    address_id  INT,
    PRIMARY KEY (customer_id, address_id),
    CONSTRAINT fk_ca_customer FOREIGN KEY (customer_id) REFERENCES Customer(customer_id)
        ON DELETE CASCADE
        ON UPDATE CASCADE,
    CONSTRAINT fk_ca_address FOREIGN KEY (address_id) REFERENCES Address(address_id)
        ON DELETE CASCADE
        ON UPDATE CASCADE
);


✅ Now, one customer can have many addresses, and one address can belong to many customers.

🔑 Summary
Relation Type	Mechanism	Example
One-to-One	Foreign key + UNIQUE	One customer ↔ one passport address
One-to-Many	Normal foreign key	One customer ↔ many addresses
Many-to-One	Same as above (reverse)	Many addresses ↔ one customer
Many-to-Many	Junction table	Customers ↔ Shared addresses

1. JOINs (Very Important)

Used when data is split across tables.

Tables:

employee

emp_id	name	dept_id
1	John	101
2	Alex	102
3	Sam	NULL

department

dept_id	dept_name
101	IT
102	HR
INNER JOIN

Returns matching records only.

SELECT e.name, d.dept_name
FROM employee e
INNER JOIN department d
ON e.dept_id = d.dept_id;
LEFT JOIN

Returns all left table rows.

SELECT e.name, d.dept_name
FROM employee e
LEFT JOIN department d
ON e.dept_id = d.dept_id;
RIGHT JOIN
SELECT e.name, d.dept_name
FROM employee e
RIGHT JOIN department d
ON e.dept_id = d.dept_id;
SELF JOIN

Employee → Manager relation.

SELECT e.name employee,
       m.name manager
FROM employee e
LEFT JOIN employee m
ON e.manager_id = m.emp_id;

Interview question:
When do you use LEFT JOIN instead of INNER JOIN?

Answer:
When you want all records from one table even if matching data does not exist.

2. GROUP BY + HAVING

GROUP BY groups data.

HAVING filters grouped data.

SELECT dept_id, COUNT(*)
FROM employee
GROUP BY dept_id
HAVING COUNT(*) > 5;

Difference:

WHERE → filters before grouping  
HAVING → filters after grouping
3. Subqueries

Query inside another query.

Find employees with salary greater than average.

SELECT *
FROM employee
WHERE salary >
(
  SELECT AVG(salary)
  FROM employee
);

Types:

Single row subquery
Multi row subquery
Correlated subquery

Correlated example:

SELECT name
FROM employee e1
WHERE salary >
(
   SELECT AVG(salary)
   FROM employee e2
   WHERE e1.dept_id = e2.dept_id
);

Temporary result set.

WITH high_salary AS

SELECT *

Use case:

Complex query readability
Recursive queries
Reusable logic

Perform calculation without collapsing rows.

ROW_NUMBER()
SELECT name,

       (ORDER BY salary DESC)

RANK()
SELECT name,
       salary,

       salary,

       (ORDER BY salary DESC)

RANK       → 1,1,3

6. Indexes (Performance)

Index makes searching faster.

CREATE INDEX idx_name
ON employee(name);

Without index:

Full table scan

With index:

Uses B-tree search

Question:

Why not create index on every column?

Answer:

Because index increases:

memory usage
insert/update cost

Since DB updates index every time data changes.

Think of indexes like the index pages in a book.

7. Normalization

Reduce duplicate data.

1NF

No repeating columns.

Bad:

| id | phone1 | phone2 |

Good:

Separate phone table.

2NF

Remove partial dependency.

3NF

Remove transitive dependency.

Example:

Bad:

| emp_id | dept_id | dept_name |

Because dept_name depends on dept_id.

Good:

Separate department table.

Interview question:

Why normalize?

Answer:

To reduce redundancy and improve consistency.

Example money transfer.

If failure:

ROLLBACK;

SQL logic stored in database.

Benefits:

When logic needs to stay close to DB and reduce repeated SQL execution.

11. ACID Properties (Very Important)

Transaction rules.

A → Atomicity

All operations succeed or all fail.

Example:

Money transfer.

If second update fails → rollback.

C → Consistency

Database remains valid.

Example:

Balance cannot become invalid.

I → Isolation

Multiple transactions should not interfere.

Example:

Two users booking same seat.

D → Durability

After commit, data stays saved.

Even after server crash.
